# Churn Early-Warning & Next-Best-Action for Digital Banking

![tests](../../actions/workflows/ci.yml/badge.svg)

> **All data in this repository is synthetic** (generated by `src/churn_nba/data.py`). No real customer information is included. Reported metrics describe the simulation, not any real bank.

Two coupled systems, one repo:

1. **Churn early-warning** - Cox Proportional Hazards (interpretable baseline) and a GRU sequence model on daily activity logs, flagging customers *weeks* before dormancy.
2. **Next-Best-Action (NBA)** - contextual bandits (LinUCB / Linear Thompson Sampling) that pick the right nudge at the moment of high intent, with a collaborative-filtering candidate generator and off-policy evaluation (IPS / SNIPS / Doubly Robust) so policies are validated *before* they touch customers.

The churn score feeds the bandit as context, so retention offers go to at-risk customers and growth offers to healthy ones.

```
 events [N,days,channels] --> landmark features --> Cox PH ----\
        |                                                      +--> churn_prob_30d --+
        +--> last-56-day sequences ---------> GRU ------------/                       |
                                                                                     v
 session signals (intent, salary just landed, low balance) ---> context x ---> LinTS bandit --> action + propensity
                                                                                     ^                  |
                                       FastAPI  /v1/nba/feedback  (online update) ---+------ decisions.jsonl (for OPE)
```

## Quickstart (Windows / PowerShell)

```powershell
python -m venv .venv ; .venv\Scripts\Activate.ps1
pip install -r requirements.txt            # CPU torch: pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -e .
pytest -q                                   # ~10 s, no torch needed
python -m churn_nba.pipeline --out artifacts            # full run incl. GRU (~2-3 min CPU)
python -m churn_nba.pipeline --out artifacts --no-sequence   # ~10 s, skips GRU

# Train from the shipped customer CSV instead of the simulator (Cox + NBA; no GRU, see below)
python -m churn_nba.pipeline --data data/churn_data_1000_clean.csv --out artifacts
python scripts/make_dataset.py              # regenerate the CSV (byte-identical; pinned by a test)

python -m churn_nba.serve --artifacts artifacts    # then open http://127.0.0.1:8000/docs
```

```powershell
curl.exe -X POST localhost:8000/v1/churn/score -H "Content-Type: application/json" -d "{\"customer_id\": \"CUST100001\"}"
curl.exe -X POST localhost:8000/v1/nba/recommend -H "Content-Type: application/json" -d "{\"customer_id\": \"CUST100001\", \"session\": {\"intent\": 1.5, \"salary_recent\": true}}"
curl.exe -X POST localhost:8000/v1/nba/feedback -H "Content-Type: application/json" -d "{\"decision_id\": \"<from above>\", \"reward\": 1}"
```

Customer IDs are strings. In CSV mode they are the `customer_id` column (e.g. `CUST100001`); in simulator mode they are `"0"`, `"1"`, ... Use the IDs in `artifacts/features_scored.csv`.

Serving guardrails built in: frequency cap (`contacts_last_7d >= 2` -> no action), per-request `eligible_actions` allow-list (compliance/eligibility), logged propensities, and a `/v1/admin/checkpoint` to persist the online-updated bandit.

**Can't reach the server?** (1) The terminal running `serve` must stay open and show `API ready`; if it exits, the message says what is missing (usually: run the pipeline first). (2) Use `http://127.0.0.1:8000/docs` in the browser, not `0.0.0.0`. (3) Visiting `/v1/...` URLs in a browser shows "405 Method Not Allowed" because those are POST endpoints; use `/docs` or `Invoke-RestMethod`. (4) Port busy: add `--port 8010`.

## Results (simulated data, 8,000 customers, seed 42)

All numbers below are on **synthetic data** with a known ground truth. They show the pipeline works and the methods are wired correctly; they are *not* a forecast of performance on your real book.

| Churn (held-out customers, 30-day horizon, 7.3% base rate) | Value |
|---|---|
| Cox PH - AUC / c-index | 0.75 / 0.65 |
| Cox PH - top-decile lift / capture of churners | 3.4x / 34% |
| GRU - AUC (same label) | 0.74 |
| Cox + GRU blend - AUC | 0.75 |

| NBA (true acceptance rate on held-out events) | Accept rate | vs random |
|---|---|---|
| Random | 14.7% | - |
| Best single arm | 17.8% | +21% |
| LinUCB (replay-trained) | 30.1% | +104% |
| LinTS (replay-trained) | 30.2% | +105% |
| Supervised greedy (per-arm logistic) | 31.2% | +112% |
| Oracle (knows true probabilities) | 31.3% | +112% |

OPE check on the LinTS policy (true value 30.2%): IPS 29.0%, SNIPS 29.7%, DR 29.9%. Collaborative filtering hit-rate@3: 0.74 vs 0.57 popularity baseline.

Honest read: the supervised per-arm model matches or edges the bandits here because the simulated log is large, uniform-random and stationary. Bandits earn their keep when the log is small, the offer catalogue changes, customer behaviour drifts, or you need to keep exploring - which is the production reality. Ship Thompson sampling, but keep the supervised model as the challenger you OPE against.

## The dataset (`data/churn_data_1000_clean.csv`)

One row per customer, 21 columns, snapshot features computed only from the 120 days before the snapshot, plus outcomes (`followup_days`, `churn_event`, `churned_30d`). `src/churn_nba/dataset.py` is the single source of truth: `make_dataset()` generates and cleans it, `load_churn_csv()` converts it into the model's feature frame, and a test asserts the shipped CSV equals `make_dataset()` output, so the file and the code cannot drift apart. Cleaning rules: tenure capped at time since age 16 (22 rows fixed), consistent rounding, sorted by ID, validation of nulls/duplicates/range/logic. The 184 rows with `followup_days < 120` and `churn_event = 0` are legitimate right-censored customers and are kept.

CSV mode trains Cox on the CSV and the bandit on simulated NBA interactions whose context uses each customer's CSV features and churn score (there is no real action log in a churn snapshot). It cannot train the GRU, which needs daily event logs. With only 1,000 customers the held-out set is ~300 customers / ~25 30-day churners, so CSV-mode metrics are noisy (AUC around 0.80 in the shipped run); treat them as a smoke test, not a benchmark.

## Moving to real data

Replace `simulate_customers` with a warehouse extract that returns the same two objects: a `customers` frame (`customer_id`, `tenure_at_start`, `age`, `n_products`, `salary_customer`, `avg_balance`, `churn_day`) and an `events` tensor `[N, days, CHANNELS]` (logins, txns, spend, failed txns, support contacts, salary deposits). Then check, in this order:

1. **Define churn precisely.** The sim uses "dormancy start" (no activity). Pick your own (e.g. 45 days no login *and* no transaction, or primary-account loss via salary diversion) and compute `churn_day` from it. Everything downstream depends on this.
2. **Censoring.** Customers who haven't churned by the end of the window are right-censored; `make_survival_frame` shows the handling. The GRU labels in this repo use ground truth (available only in simulation) - on real data use a censoring-aware label or train on landmarks where the full horizon is observed.
3. **Leakage.** Features must be computable at the landmark with data you'd actually have then (watch late-arriving transactions and backfilled dormancy flags).
4. **Time-based splits.** Replace the random customer split with train-on-earlier / test-on-later landmarks.
5. **Calibration.** Check `churn_prob_30d` against observed rates by decile before using it to size retention budgets.
6. **Real logged propensities.** Roll out Thompson sampling to a small traffic slice with a permanent random-holdout (5%) and a no-contact control. The holdout is what makes OPE and incrementality measurement trustworthy. The bandit here learns *acceptance*; if the goal is retention uplift, log retained-vs-churned outcomes against a control and optimise that.
7. **Governance.** Offers touching credit (loan prefill, card offers) need affordability, fair-lending and consent checks before they enter `eligible_actions`. Audit action mix and acceptance by protected-class proxies. Keep the Cox driver output (`top_risk_drivers`) so relationship managers can see why a customer was flagged.

## Known limitations

- Linear-reward bandit on binary outcomes is an approximation; swap in logistic Thompson sampling or a neural bandit once the baseline is trusted.
- Cox assumes proportional hazards; a sharp "imminent decay" effect is better captured by time-varying covariates or the GRU. The blend is a simple average - stack on a validation set for real use.
- The GRU is evaluated at one landmark; production should evaluate rolling.
- In-memory pending-decision store and bandit state: run a single API worker, or move state to Redis/Postgres for horizontal scaling.
